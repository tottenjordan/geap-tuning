# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A collection of **working, runnable examples** demonstrating **Gemini Enterprise Agent Platform (GEAP)** model tuning services. GEAP is Google Cloud's rebrand/evolution of the Vertex AI Agent Platform surface; its tuning APIs are reached through the same `aiplatform.googleapis.com` endpoints and the Python SDKs below.

## Code standards (read first)

**Always refer to [CODE_STANDARDS.md](CODE_STANDARDS.md) before writing code or making environment changes**, and link to it when you do. Non-negotiables: `uv` for all package management (never bare `pip`/`python`), `ruff` for lint+format, `ty` for type checks, `pytest` for tests, and **never** add `Co-Authored-By` trailers to commits/PRs.

## Layout & commands

Python `src/` layout, package `geap_tuning`, managed by `uv` (Python 3.12+). Config and tool settings live in `pyproject.toml`; `Makefile` wraps the common flows:

- `make dev` — `uv sync --all-groups` (install runtime + lint + test groups)
- `make lint` — `ruff format --check` + `ruff check` + `ty check src/`
- `make format` — `ruff format .`
- `make test` — `uv run pytest` (coverage on `geap_tuning`)
- Single test: `uv run pytest tests/test_smoke.py::test_main_runs`

Runtime deps: `google-genai`, `google-cloud-aiplatform` (Vertex/Agent Platform SDK), `python-dotenv`. The repo is still early — one placeholder entry point (`geap_tuning.main`) and a smoke test; add tuning examples as their own modules under `src/geap_tuning/`.

## Tuning surface being demonstrated

This repo demonstrates GEAP's **three** tuning services (one example subpackage each under `src/geap_tuning/`):
- **Supervised fine-tuning (SFT)** — the core method; teaches a new skill/behavior from labeled JSONL examples (`contents` records). Implemented (`sft/`). **Multimodal (image) SFT** is also demonstrated (`sft_vision/` — oral-disease image classification, ported from jswortz/dental-fine-tune-26): records carry a `fileData` image part, but the tune call is **identical** to text SFT so it reuses `sft.tune.launch_sft_job` (no new tune module). Dataset via optional `vision` group (`kagglehub`, lazy-imported; needs `KAGGLE_API_TOKEN`); demoed by `examples/run_sft_vision.py`/`notebooks/09_sft_vision.ipynb` with a hyperparameter sweep → val-select → test. See [docs/notes/multimodal-sft.md](docs/notes/multimodal-sft.md). Also demonstrated on a **generative structured-output** task (not just classification): messy text → strict JSON extraction (`sft/extraction.py` + `sft/extraction_eval.py`, headline field-exact-match `accuracy` with type-headroom via an int `quantity`), a before→after lift in `examples/run_sft_extraction.py`/`notebooks/17_sft_extraction.ipynb`.
- **Preference tuning (DPO)** — builds on SFT using preference pairs; same `client.tunings.tune(...)` call with `method="PREFERENCE_TUNING"` + a `beta` hyperparameter, and `completions`/`score` in each record. Implemented (`preference/`). A second domain — **concise professional email rewriting** (`preference/email.py` + `preference/email_eval.py`) — records a measured before→after: a blind A/B autorater `win_rate` (judge prompt distinct from the generator; both completions carry the same facts so it grades style) backed by an objective `mean_compression`, in `examples/run_preference_email.py`/`notebooks/18_preference_email.ipynb`.
- **Reinforcement learning fine-tuning (RLFT)** — trains against a programmable **reward function** over a `references` dataset (no target completion). The installed Gen AI SDK supports it on the *same* `client.tunings.tune(...)` call with `method="REINFORCEMENT_TUNING"` + a `reward_config` (still Pre-GA/`v1beta1`, so verify symbols before running). Implemented (`rlft/`). All **four** reward scorers now have builders (`build_{reward,string_match_reward,autorater_reward,cloud_run_reward}_config`; cloud-run is documented-only) plus `build_composite_reward_config` for weighted combinations — toured by `examples/run_rlft_reward_types.py`/`notebooks/06_rlft_reward_types.ipynb`. Also demonstrated on **graded constrained generation** (`rlft/constrained.py` + `rlft/constraint_reward.py` + `rlft/constraint_eval.py`): each prompt spells out four constraint types at once and the reward is the *fraction* of independently-checked components satisfied — the reachable graded-reward design that answers the two prior RLFT nulls (variance ⇒ gradient; four-at-once ⇒ headroom). `build_reward_config` gained a `module=` kwarg so any stdlib-only reward ships via `inspect.getsource`. Before→after (with a `--pilot-only` headroom gate + `bootstrap_ci`) in `examples/run_rlft_constrained.py`/`notebooks/19_rlft_constrained.ipynb`. See [docs/notes/generative-tuning-domains.md](docs/notes/generative-tuning-domains.md).

Checkpoints and continuous tuning are cross-cutting sub-features of these services, not separate services — both are now **demonstrated** via shared helpers in `jobs.py` + launcher params (`export_last_checkpoint_only`, `evaluation_config`, `pre_tuned_model_checkpoint_id`; RLFT also `evaluate_interval` + `checkpoint_interval` — both are RLFT-only in google-genai 2.14.0, which serializes them under `reinforcementTuningSpec`, so SFT/DPO jobs 400 if given `evaluate_interval`) and dedicated demos (`examples/run_checkpoints.py`/`notebooks/04_checkpoints.ipynb`, `examples/run_continuous_tuning.py`/`notebooks/05_continuous_tuning.ipynb`, an SFT→RLFT chain). See [docs/notes/checkpoints-and-continuous-tuning.md](docs/notes/checkpoints-and-continuous-tuning.md). **Managed evaluation** is likewise cross-cutting — reached only via `CreateTuningJobConfig.evaluation_config` (no standalone `client.evals` in 2.14.0); `autoeval.py` builds it (`llm_judge_metric`/`computation_metric`/`predefined_metric`, `build_autorater_config`, `inference_generation_config`), demoed comprehensively by `examples/run_advanced_eval.py`/`notebooks/07_advanced_eval.ipynb` (`us-central1`-only, Preview). **Experiment tracking** is two layers (see [docs/notes/experiment-tracking.md](docs/notes/experiment-tracking.md)): Layer 1 (automatic per-job train/val curves in the console Monitor tab — no code) and Layer 2 (opt-in Vertex AI Experiments + Managed TensorBoard). Layer 2 is now **implemented** via `src/geap_tuning/experiments.py` (`init_experiment`, `get_or_create_tensorboard`, `track_run`, `log_summary_metrics`, `log_timeseries_metrics`, `experiment_dataframe`) and demoed for SFT by `examples/run_experiment_tracking.py`/`notebooks/08_experiment_tracking.ipynb` and identically for RLFT by `examples/run_rlft_experiment_tracking.py`/`notebooks/13_rlft_experiment_tracking.ipynb` (cheap `gemini-2.5-flash` + string-match reward; metric values are our offline per-checkpoint `run_rlft_eval`, not job-emitted reward) — TensorBoard is opt-in (`--tensorboard`, default off) since it carries cost; summary metrics need none. This is the one sanctioned SDK mix (`google-cloud-aiplatform` orchestrating around the `google.genai` tune call). `jobs.py` also exposes `cancel_tuning_job`/`cancel_tuning_job_by_display_name` (tuning jobs are cancellable while non-terminal but not deletable — see [docs/notes/endpoints-and-cost.md](docs/notes/endpoints-and-cost.md)). **DOE (design of experiments) + multi-run visualization** is likewise cross-cutting: `src/geap_tuning/doe.py` declares a full-factorial hyperparameter sweep (`SweepConfig`, `method`-keyed for **SFT/DPO/RLFT** via the `_LAUNCHERS` registry) and runs it as a unit (`run_sweep` — idempotent reuse by display name, offline eval, Experiments logging via the sanctioned mix point; `expand_grid`/`build_run_specs`/`aggregate_results`/`select_best_run`/`collect_checkpoint_curve` are pure and unit-tested). Per-method reporting via `HEADLINE_METRIC`/`METRICS_BY_METHOD` (DPO headlines `win_rate`, not accuracy); a non-scalar RLFT `reward_config` rides in `sweep.fixed` and is filtered from rows/Experiments params by `_scalar_params`. `src/geap_tuning/viz.py` plots the runs (`plot_metric_bars`/`plot_grouped_metric_bars`/`plot_curves`, `normalize_experiment_rows` bridges `experiment_dataframe` columns) via the optional `viz` group (matplotlib+pandas, lazy-imported like the `vision` group). Demoed by `examples/run_doe.py`/`notebooks/10_doe.ipynb` (SFT sweep), `examples/run_doe_dpo.py`+`examples/run_doe_rlft.py`/`notebooks/12_doe_dpo_rlft.ipynb` (DPO & RLFT hyperparameter sweeps), `examples/run_doe_rlft_rewards.py`/`notebooks/15_doe_reward_types.ipynb` (RLFT **reward-shape** sweep — one single-run `SweepConfig` per reward builder in `sweep.fixed`, combined under driver-owned labels vs. an untuned `gemini-3.5-flash` baseline; no `doe.py` change — but a **flat null result**: the base saturates the task, so it ranks nothing and is kept as the cautionary tale), `examples/run_doe_rlft_reward_ranking.py`/`notebooks/16_doe_reward_ranking.ipynb` (the **rank-capable** redesign of that sweep — same orchestration, but a neutral marker-free instruction + harder tiered bank in the new `rlft/bench.py`, a pilot headroom gate (`--pilot-only` scores it with no spend), and multi-axis scoring via `evaluate.run_rlft_multimetric_eval` + `bootstrap_ci` CIs. **Key finding — a second, deeper null (ran live on `gemini-3.5-flash`).** Two levers were meant to make it rank; both failed. (1) The "weaker base for correctness headroom" lever does not work — every reachable base saturates verifiable math (correctness 0.90–0.97 across three pilots, weakest 2.5 base included), and GEAP docs point to `gemini-3.5-flash` as the RLFT base anyway, so `correctness` is only a saturated control. (2) The neutral instruction *did* open full `format_rate` headroom (baseline 0.000), but **RLFT still couldn't teach the `Answer:` marker — even the `string-match` reward (regex is the exact marker) left `format_rate` at 0.000** (verified by probing the tuned endpoint). Root cause: the base emits the marker ≈0% of the time, so every rollout earns the same format reward → no advantage signal → no gradient. **RL amplifies behaviors the base sometimes produces; it can't bootstrap a from-scratch output format without an SFT warm-start first.** `explanation_quality` was also pinned at 1.000 (too-lenient judge), so no axis ranks. The redesign was sound (headroom was created and measured); the null is a genuine property of reinforcement tuning — a more instructive result than a tidy leaderboard. The driver now isolates each shape (a transient job failure is skipped, not fatal). See [docs/doe/rlft-reward-ranking/README.md](docs/doe/rlft-reward-ranking/README.md)), and the read-only `examples/run_multi_run_viz.py`/`notebooks/11_multi_run_viz.ipynb` (charts an existing Experiment, zero tuning cost). The demo SFT sweep (`geap-doe-sft`) **saturates at accuracy=1.0** on its easy 5-intent set (can't discriminate), so a second **discriminating** SFT DOE runs the same grid on **banking77** (77 fine-grained intents, sourced via stdlib — no dep — by `src/geap_tuning/sft/banking.py`; see [docs/notes/banking77-dataset.md](docs/notes/banking77-dataset.md)) **plus an untuned baseline** (scored + logged in the driver, not `run_sweep`, for a before→after story), demoed by `examples/run_doe_banking77.py`/`notebooks/14_doe_banking77.ipynb` — no `doe.py` change. Key constraint: Layer-1 Monitor loss curves are console-only (not SDK-fetchable), so cross-run curves come from our offline per-checkpoint eval. See [docs/notes/doe-and-visualization.md](docs/notes/doe-and-visualization.md). Data modalities: text, image, audio, document. Datasets are JSONL files staged in Cloud Storage. Full API shapes are in [docs/notes/tuning-apis.md](docs/notes/tuning-apis.md).

## Two SDK paths (pick deliberately; do not mix in one example)

Examples generally follow one of two client styles. Keep each example on one path so it reads cleanly:

1. **Google Gen AI SDK** — `from google import genai`; `client.tunings.tune/get/list(...)` (the launch method is `tune`, not `create`). Routes to Vertex when constructed with `vertexai=True` (or `GOOGLE_GENAI_USE_VERTEXAI=true`). This is the newer, preferred surface and the one this repo uses.
2. **Agent Platform / Vertex SDK for Python** — `import vertexai` + `from vertexai.tuning import sft`; `sft.SupervisedTuningJob(...)`. Older but appears throughout Google's tuning docs.

A tuning job's output is an **endpoint** (`tuning_job.tuned_model.endpoint`); you call `generate_content` against that endpoint, not a model name. For thinking models, disable thinking / set the minimum thinking budget when calling a tuned model — SFT trains the model to mimic ground truth without a thinking trace.

## Environment / configuration

Config lives in `.env` (present, git-ignored — never commit it). Load it before running any example. Key groups:
- **GCP project**: `PROJECT_ID`, `GOOGLE_CLOUD_PROJECT`, `GOOGLE_CLOUD_PROJECT_NUMBER`, `GCP_REGION`, `GOOGLE_CLOUD_LOCATION`.
- **API routing / auth**: `GOOGLE_GENAI_USE_VERTEXAI` (true → Vertex/GEAP path), `GOOGLE_API_KEY` / `GEMINI_API_KEY` (AI Studio / Developer API path).
- **Cloud Storage** (dataset + checkpoint staging): `GCS_BUCKET_NAME`, `BUCKET`, `GOOGLE_CLOUD_STORAGE_BUCKET`.
- **Resource labels**: `LABEL_KEY` / `LABEL_VALUE` (defaults `project` / `geap-tuning`) → resolved once into `cfg.labels` (a `{key: value}` map, empty when either is unset). Every resource the repo creates is labeled from `cfg.labels`: the three tuning-job launchers pass it into `CreateTuningJobConfig(labels=...)` (GEAP propagates it to the generated Model + Endpoint) and `experiments.get_or_create_tensorboard` labels a newly created Managed TensorBoard. `aiplatform.init`/`start_run` and GCS objects have no resource-label param, so they're excluded. Backward-compatible (unset ⇒ `labels=None`, a no-op) and Vertex-path-only. See [docs/notes/resource-labels.md](docs/notes/resource-labels.md).

Note the redundant aliases (`PROJECT_ID`/`GOOGLE_CLOUD_PROJECT`, three bucket vars). When writing an example, decide which var name it reads and be consistent; don't assume all three buckets point at the same place.

Most tuning docs default examples to `us-central1`. The Gen AI evaluation service that can auto-run after a job is (per docs) available in `us-central1` — prefer it for examples that chain tuning → eval.

Auth for CLI/REST calls: `gcloud auth print-access-token` (user must have run `gcloud auth login`). If you need the user to authenticate, suggest they run `! gcloud auth login` in the prompt.
